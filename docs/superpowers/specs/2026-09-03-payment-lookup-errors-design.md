# Семантика отсутствующего ресурса в Bedolaga MCP

Дата: 2026-09-03. Репозиторий: bedolaga-mcp. Ветка: codex/payment-lookup-errors.
Статус: подготовлено Sol для согласования; разрешения на реализацию нет.

## Проблема

BedolagaClient._request_json в bedolaga_mcp/client.py сейчас превращает любой HTTP 404 в UserNotFoundError. Метод общий для поиска пользователя и финансовых, реферальных, подписочных и других ресурсов, через _get, _get_object и _get_list. Поэтому успешный lookup пользователя с последующим 404 истории транзакций приводит к ложному structured error user_not_found. Модель поддержки может ошибочно сообщить, что аккаунта нет.

## Решение и контракт

Только два явных пользовательских lookup — get_user_by_telegram_id и get_user_by_id — имеют право трактовать свой 404 как UserNotFoundError. Контекст операции должен передаваться в общий HTTP-слой явно и безопасно по умолчанию: обычный запрос ресурса не является поиском пользователя. Не определять тип операции по вхождению идентификатора пользователя в путь или параметры.

404 любой другой операции возвращает существующий UpstreamUnavailableError с кратким безопасным сообщением о недоступном запрошенном ресурсе Bedolaga, без утверждения отсутствия пользователя. Сохраняются десять кодов SPEC_ERROR_CODES и действующий retryable для upstream_unavailable: true. Этот флаг обозначает существующую категорию ошибки, не обещает успешного повтора и не требует добавлять автоматические повторные запросы.

Существующие публичные методы, формы успешных ответов и structured envelope сохраняются. Registry должен пропускать доменную ошибку без подмены на user_not_found или internal_error. Код user_not_found остаётся невосстанавливаемым и описывает лишь подтверждённый результат текущего lookup. README явно различает отсутствие пользователя и отказ отдельного ресурса.

Изменение не превращает 404 коллекции в успешный пустой список и не превращает отсутствие опционального поля в ошибку. Существующие успешные пустые коллекции, null и необязательные вложенные данные обрабатываются как раньше. Специальной новой трактовки «опциональный ресурс отсутствует» не вводится; существующая локальная обработка, если найдётся при реализации, должна сохранить подтверждённую семантику и не маскировать ошибки обязательной истории платежей.

401/403, 422, 429, 5xx, сетевые ошибки, таймауты, ошибки JSON и форм ответов сохраняют действующее отображение. Без изменения идентичности, allowlist, HTTP read-only, обработки секретов, нормализации денег, пагинации и финансовых выводов. Не включать содержимое ответа upstream, ключ, полный URL или идентификаторы в новые сообщения ошибки.

## Приёмка

Offline HTTP-тесты проверяют 404 обоих lookup и всех существующих непользовательских семейств: transactions, referrers, subscriptions, tickets, promo-codes. Проверяется также безопасная трактовка обычного общего запроса. Успешные ответы и прежние отображения статусов сохраняются.

Интеграционная регрессия проходит через настоящий client и registry с синтетическим HTTP: успешный lookup и 404 transactions дают envelope upstream_unavailable с retryable true; lookup 404 даёт user_not_found с retryable false и не запускает дальнейшую историю. Проверяются служебные поля envelope и отсутствие секретов. tests/test_contracts.py подтверждает прежний набор кодов и флагов; существующие тесты инструментов, identity и transport security остаются зелёными.

Ворота репозитория из .github/workflows/ci.yml: Python 3.14, весь unittest discover и smoke импорта пакета и реестра всех восьми инструментов. Отдельных обязательных lint, type и coverage-порогов здесь нет; новые ворота не добавляются и не выдаются за существующие. Реальные Bedolaga API и клиентские данные не используются.

## Объём и согласование

Реализация ограничена client, связанными проверками и уточнением документации ошибки; errors.py и contracts.py меняются только при необходимости поправить описание, без новых кодов. Соседний план supportBot изменяет трактовку ошибок моделью и сценарии оплаты отдельно. Реализацию и тесты пишет только Gemini 3.8 Flash после явного согласования человеком; Sol выполняет review. Без live API, новых API-ключей, смены провайдера, deployment, push, merge и изменения версии.
